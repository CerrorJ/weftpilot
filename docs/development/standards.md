# 开发规范 v0.2

面向另一台设备上的 Codex 和开发者。按用户要求增加中文注释、原子性、单一职责、代码可读性和文件规模约束；内核采用 Agent-Team 打包复用，首版 macOS/Windows。当前仅更新文档，下文工具规则和命令在正式工程阶段落地。

## 1. 需求与实现依据

- 架构选择以用户确认记录为准，产品行为参考 `product-design` 分支的角色、任务和验收流程。
- 区分已实现、模拟、待实现和待验证，不用截图、静态页面或一次正常路径证明真实集成完成。
- 接到功能需求后明确触发条件、输入、结果、失败方式和验收证据，再编写实现。
- 重大架构变更记录 ADR：问题、备选、决策、代价、验证和替代关系；一般实现细节不要求反复确认。

## 2. 工程与依赖

- 使用 TypeScript strict、ESM，建议启用 `noUncheckedIndexedAccess`、`exactOptionalPropertyTypes`；各运行环境分别配置类型，不向渲染层注入 Node 全局。
- 纬舟使用 pnpm workspace，内部依赖用 `workspace:*`；两仓各自提交锁文件，CI 冻结安装。共享内核与协议由 Agent-Team 发布，纬舟锁定版本和摘要，不以跨仓 `workspace:*` 引用假装发行依赖。参考 [pnpm workspace 官方文档](https://pnpm.io/workspaces)。
- 初始化时固定 Node、pnpm、Electron、React、构建工具和检查工具的兼容版本，记录在仓库；不盲目选择最新版或各设备自行升级。
- 本机 Node 与 Electron 内嵌 Node/Chromium 分别记录。SQLite 原生模块必须验证打包后的 ABI、签名、目标架构，不能只验证 Node 开发环境。
- 新依赖写明用途、维护状态、许可和成本；本项目设计工具不使用付费生成能力。不要为暂未实现的未来功能引入整套框架。
- 开发/测试/发行配置分开，提供无凭据的示例；启动时校验缺失配置并给出明确错误。

## 3. 单一职责、中文注释与可读性

### 3.1 设计原则

- 以单一职责为基本要求：函数围绕一个动作、模块围绕一个领域能力、组件围绕一项界面职责；只有同一类业务变化才应修改同一模块。
- 分离读取和修改、校验和副作用、业务规则和展示。避免一个函数同时解析飞书消息、写数据库、启动进程并生成 UI。
- 低耦合高内聚，依赖倒置；内核领域层无数据库、SDK、文件、系统时钟和进程 I/O，应用层通过端口取得能力。
- 优先组合与明确数据结构，接口按消费方拆小；不为套用 SOLID 增加无用途的继承层或服务类。
- DRY 仅针对相同业务知识，允许暂时相似但演化方向不同的代码；遵循 KISS/YAGNI，不提前实现未要求的通用框架。
- 状态转换由内核集中裁决，不在纬舟客户端再写一份判断；公共契约由 Agent-Team 维护并发布。

### 3.2 适量中文注释

- 公共内核 API、端口和跨进程契约采用中文 JSDoc，说明用途、不变量、副作用、关键错误、取消/超时和幂等语义；参数和类型已明确的内容无需重复。
- 状态机、事务/锁边界、审批和恢复、平台差异、重试限制及非显然算法添加中文实现注释，解释“为什么这样做”和“不能破坏什么”。
- 普通内部函数命名清楚且逻辑直接时无需注释，不逐行翻译赋值、循环和条件，不要求机械注释覆盖率。
- 保留必要技术名词、协议字段和第三方原文标识；业务解释优先中文。修改行为时同步修改相关注释，删除失效注释和被注释掉的旧代码。
- TODO/FIXME 写明原因、关联任务/问题或可执行的后续动作；不能用 TODO 掩盖当前成功路径中缺失的关键实现。

```ts
/**
 * 提交当前审批决定；使用请求版本进行比较交换。
 * 重复请求返回既有结果，旧版本决定不得影响后续执行片段。
 */
async function resolveApproval(command: ResolveApprovalCommand) {
  // 先持久化决定与 outbox，事务外再发送飞书通知，避免锁跨越网络等待。
  return approvals.resolve(command);
}
```

示例仅说明注释风格，不代表已存在此接口或实现。

### 3.3 可读性

- 文件 kebab-case，组件/类型 PascalCase，函数/变量 camelCase；使用完整业务名称和明确布尔谓词，避免无上下文缩写。
- 优先早返回与命名中间结果，避免多层条件、嵌套三元、过长链式调用、魔法数字和布尔位置参数。
- 多个同类参数使用有含义的参数对象；错误分支明确，Promise 不悬空，不用 `any`、非空断言或忽略检查代替校验。
- 无共享用途的函数放在所属模块附近，不建立无边界的巨型 utils；拆分围绕真实职责，禁止为凑行数创建无意义跳转。
- 格式由 Prettier 统一：建议 2 空格、100 列打印宽度；宽度是格式目标，不强行切断 URL、字符串或类型降低可读性。

### 3.4 文件与函数规模

以下是本项目可执行的规模约定，不是所有社区的统一标准。有效行按格式化后的文件统计，排除空行和纯注释行；物理行包含全部内容，避免大文件因排除注释而失控。

| 项目                      | 目标/上限                                             | 检查方式                      |
| ------------------------- | ----------------------------------------------------- | ----------------------------- |
| 普通手写 TS/TSX/JS 源文件 | 目标不超过 200 有效行，硬上限 300 有效行且 500 物理行 | `max-lines` + 物理行脚本      |
| 手写测试文件              | 上限 600 有效行且 800 物理行，优先按行为拆分          | 测试目录覆盖规则 + 物理行脚本 |
| 普通函数/组件/方法        | 目标 20–30 有效行，硬上限 50 有效行                   | `max-lines-per-function`      |
| 代码嵌套                  | 最多 3 层                                             | `max-depth`                   |
| 圈复杂度                  | 最多 10                                               | `complexity`                  |
| 函数参数                  | 最多 4 个；复杂输入优先对象                           | `max-params`                  |

JSX、import 和类型声明仍计入有效行；不能将多条语句挤成一行、删掉必要注释、把整段代码搬进匿名回调规避限制。大型 React 视图按有意义的区域和状态职责拆分。

生成代码、协议产物、数据库迁移、脱敏事件夹具和纯数据表可按明确路径例外；保留来源、生成方式与专用验证，不能全局关闭规则。测试套件容器回调可设置明确例外，测试业务 helper 不一并豁免。

超限特例写明文件/函数、原因、上限、验证和治理计划，范围精确到对象。Agent-Team 历史大文件采用基线治理：不新增超限，不扩大已有问题，修改涉及的职责逐步抽取，不在无关功能中强行全仓重构。

M0 在实际配置中建立以下普通源码规则，并单独配置测试/生成路径；物理行检查另行实现，不把文档示例视为 CI 已生效：

```js
const sourceSizeRules = {
  "max-lines": [
    "error",
    { max: 300, skipBlankLines: true, skipComments: true },
  ],
  "max-lines-per-function": [
    "error",
    {
      max: 50,
      skipBlankLines: true,
      skipComments: true,
      IIFEs: true,
    },
  ],
  "max-depth": ["error", 3],
  complexity: ["error", 10],
  "max-params": ["error", 4],
};
```

## 3A. 原子性与副作用边界

- **业务原子性**：一次命令定义清楚成功/失败边界。对象修改、事件、outbox 和幂等回执在一个事务提交，失败全部回滚；不将网络调用或长时间 CLI 执行放在持有锁的数据库事务中。
- **外部副作用**：数据库与进程/Git/飞书不能天然共同回滚。使用持久意图、幂等键、状态对账、明确补偿和失败恢复；无法证明未执行的动作不自动重跑。
- **文件与配置**：先校验完整内容，在同一文件系统写临时文件并完成所需落盘，再替换正式文件；保留旧版本/恢复路径，避免半写配置。跨卷操作不能假定 rename 原子。
- **技能和内核安装**：临时目录准备、内容/兼容校验、完成后切换版本引用；中断时不破坏上个可用版本，清理不能删除仍被运行引用的版本。
- **代码提交**：一次提交聚焦一个可解释、可构建/验证的目的，避免功能、全仓格式化和无关重构混合。两仓分别提交，通过关联版本与兼容发布衔接，不声称跨仓 Git 提交具有事务原子性。

## 4. 状态与并发

- 状态转换集中定义，由内核应用用例裁决；禁止组件、卡片处理器、CLI adapter 各自修改同一业务状态。
- 修改对象使用版本比较交换；并发冲突返回明确错误，不采用最后写入覆盖审批结果。
- 业务状态、事件和命令回执在同一数据库事务提交；通知在提交后通过 outbox 投递。
- 命令具有幂等键和请求内容摘要；相同键不同内容拒绝，重试不得重复创建 Run 或重复触发外部动作。
- 重试已结束执行产生新 Run；非终态审批续接产生新 ExecutionSegment；两者不得混用。
- 并发资源用持久状态与内核调度共同控制，不能只靠前端禁用按钮或内存布尔值。
- 外部动作不存在天然 exactly-once；执行状态未知时先对账，禁止直接自动重跑。
- 所有时长、重试、超时和队列容量有明确上限；取消信号逐层传递，释放锁和句柄需保证可重复执行。

## 5. CLI、Git、模型与 Skill

- CLI adapter 只处理协议、能力、参数和事件归一化，不承担任务状态机和飞书展示。
- 执行器使用明确可执行文件、参数数组和 `shell: false`；不拼接用户输入为 shell 命令，平台差异写在 adapter。
- 记录原生会话和执行片段，测试进程树终止、超时、中文/空格路径及非零退出。
- 项目 Git 操作始终明确仓库、工作目录和分支；执行前检查脏文件与冲突，不执行隐式 reset、clean、强制切分支或覆盖。
- 默认 Run 隔离目录；清理先确认无活动进程、无保留交付且得到相应清理授权。
- 模型参数依据提供方和 CLI 能力校验；认证、限流、网络、上下文不足和工具失败分别分类。
- 用量和费用允许未知，估算明确标记依据；没有提供方数据不显示虚构精确金额。
- Skill 固定来源和版本/摘要；安装、启用和执行分开。升级影响新 Run，旧快照保持可解释。
- 不默认执行 Skill 包中的安装脚本；声明权限与实际执行权限不一致时阻塞或明确降级。

## 6. 桌面界面

- 复用品牌 SVG 与产品设计的视觉变量；业务状态使用文字、图标和颜色共同表达。
- 页面按工作台、项目、任务、需求、角色、团队、技能、设置组织，按真实能力逐步接入。
- 表单处理空、加载、失败、不可用、校验和成功；长流程保存草稿，异步动作显示受理与执行结果的区别。
- 进度显示阶段、等待原因、最后活动和可用动作；步骤总数未知时不伪造百分比。
- 运行、停止中、已停止、状态待确认分别呈现；重试展示新 Run，历史可查。
- 浏览器存储只存非敏感界面偏好，不作为任务数据库；新输入凭据不进入共享状态或日志。
- 支持键盘操作、可见焦点、表单标签、合理对比度；大列表分页或虚拟化。
- 渲染层不读取任意本机路径或打开任意 URL；预览不执行外部脚本，原始 IPC 不暴露给页面。

## 7. 日志、错误与数据

- 结构化日志带 correlationId、workspaceId、taskId、runId、segmentId（按场景选择）、事件类型和耗时。
- 默认脱敏，禁止记录密钥、认证头、Cookie、CLI 认证文件和未经处理的完整用户内容。
- 原始 CLI 输出与业务事件分流，设置文件大小、轮转和保留期限；诊断包支持预览并明确导出。
- 错误包含稳定 code、可理解的中文提示、是否可重试及关联 ID；不吞掉异常或无证据返回成功。
- 数据迁移不可改写已发布版本，迁移前备份并验证恢复。变更字段应考虑旧数据和旧事件的读取。
- 归档与删除区分；有 Run/交付引用的角色或 Skill 版本不能直接硬删除。

## 8. 测试与质量门槛

按风险测试，不设脱离业务的覆盖率数字，也不为纯文案或可逆样式修改编写镜像实现的测试。

| 测试层次      | 必须覆盖的风险                                                        |
| ------------- | --------------------------------------------------------------------- |
| 领域单元      | 状态转换、归属、不可变快照、重试新 Run、验收独立                      |
| 用例/仓储集成 | SQLite 事务、CAS、幂等、任务活动 Run 唯一、outbox、迁移与恢复         |
| 契约与适配器  | IPC 校验、CLI 脱敏录制事件、飞书回调、错误归一化与兼容                |
| 进程/Git 集成 | 测试仓库、worktree、脏目录、进程终止、启动窗口崩溃与重启对账          |
| 桌面关键流程  | 创建角色/试运行、任务执行/停止/重试、审批竞争、验收退回、关闭窗口行为 |
| 原生发行验证  | 目标系统安装、凭据存储、签名/权限、升级备份恢复                       |

内核领域、CLI、持久化与原飞书入口回归在 Agent-Team 测试，桌面/桥接/内核装配在纬舟测试；协议两端做兼容验证，不只检查 TS 类型。

默认自动测试使用测试目录、替身进程和脱敏夹具，不调用付费模型、不操作真实飞书租户或生产仓库。真实集成验证必须明确测试环境、授权、成本和结果，不能用默认单测替代。

工程初始化后统一建立：

```sh
pnpm install --frozen-lockfile
pnpm lint
pnpm format:check
pnpm typecheck
pnpm test
pnpm build
pnpm test:e2e
```

这些是目标命令，当前仓库尚无相应 package.json 或实现。M0 按实际工具配置建立命令和 CI；CI 执行必要静态检查、构建与测试，桌面/发行检查按目标平台设置矩阵。未执行的项目明确注明，不声称全通过。

通过本次变更需要的检查后不无理由反复扩大测试；新失败或新风险才追加验证。

## 9. Git、评审与发布

- `main` 是正式开发主线，`product-design` 维护产品方案和原型；新分支使用 `feat/xxx`、`fix/xxx`、`docs/xxx`、`chore/xxx`，不加 `codex/`。
- 设计更新通过可追踪的实现任务落实，不把整个原型分支合并进 main。
- 提交使用 `feat(scope): 中文说明`、`fix(scope): 中文说明`、`docs: 中文说明` 等形式，一次提交围绕一个可理解的目的。
- PR 说明问题、最终行为、验证结果和已知限制；状态/协议/数据变化同步文档和迁移。涉及 Agent-Team 时允许同步改动并分别提交，记录两仓关联提交、内核版本和兼容性；先完成内核再更新桌面锁定产物。
- 不改写公共历史，不提交本地路径、缓存、构建产物、凭据和运行数据库；按来源记录迁移的旧代码和许可证。
- 建议主线通过 PR 与 CI 合入，配置分支保护由仓库所有者按协作方式决定。本轮不创建发布或自动部署流程。
- 安装包、签名、公证、自动更新和数据库降级策略在发行阶段完成验证；不能在尚未解决兼容时默认强制更新。
- 公开仓库的许可证由所有者决定；未确定前不擅自添加 MIT/Apache 等授权。发布前核验依赖、素材和迁移代码的许可。

## 10. 社区依据与项目取舍

没有一份适用于全部 TypeScript/Node 项目的“社区唯一标准”。本规范参考官方/原作者资料，并以本项目的内核复用、中文协作和跨平台约束作取舍：

- [Google TypeScript Style Guide](https://google.github.io/styleguide/tsguide.html)：命名、清晰表达、公共 API 文档与有信息量的注释；不逐条照搬 Google 内部工程假设。
- [TypeScript strict](https://www.typescriptlang.org/tsconfig/strict.html)：使用严格类型检查，依赖升级后重新验证。
- [ESLint max-lines](https://eslint.org/docs/latest/rules/max-lines) 与 [max-lines-per-function](https://eslint.org/docs/latest/rules/max-lines-per-function)：提供可配置的规模约束；默认分别为 300/50，本项目另定义有效行、物理行与例外规则。

中文注释、复杂度/嵌套/参数上限和跨仓原子提交规则属于项目约定，并非声称上述资料规定了全部阈值。

## 11. 完成与交接标准

功能完成需同时满足：需求可复现、真实能力有证据、相关失败路径可解释、必要检查通过、文档/迁移一致、已知限制如实记录。

每次交接提供当前分支和提交、完成范围、运行过的命令与结果、未完成事项及下一步。另一设备从仓库与记录继续，不依赖上一台电脑的隐藏状态。
