# Agent-Team 内核打包与两仓协作 v0.2

依据：用户明确要求将 Agent-Team 打包作为纬舟内核，需要时可以同步修改 Agent-Team。正式开发在另一台设备进行；本轮仅建立设计与协作规范。

## 1. 唯一源码与扩展原则

2026-10-22 已授权正式开发。M0 实际锁定字段与产物见 `config/kernel-lock.json`，实现和验证见 [开发交接](../development/progress.md)；下面“当前没有产物”描述的是 v0.2 设计时点，后续能力以握手为准。

- **Agent-Team**：内核源码、共享契约、CLI/模型、调度、审批、角色/团队、项目/需求/任务、Git、Skill、持久化、飞书适配器及其测试。现有缺少的领域能力在此增量实现。
- **WeftPilot**：Electron/React 桌面产品、内核进程宿主、客户端连接与投影、凭据/系统桥接、安装包组装和桌面测试。
- 纬舟使用内核产物，不复制内核源码再改，也不只复用 CLI adapter 后在桌面仓库重写其余执行逻辑。
- “可打包”需要先改造现有入口：当前 `src/index.ts` 直接加载配置并初始化飞书对象，`src/app/runtime.ts` 含 Bot 运行态，不能直接导入后宣称已获得无副作用、可独立启动的内核 API。

## 2. 封装方式

建议内核产物是编译后的 Node.js ESM 代码及必要依赖、资源和数据迁移，而不是复制源码目录或要求用户启动一个开发服务器。

Agent-Team 增加无 UI 依赖的启动/停止入口、命令分发、事件订阅和健康/能力查询。创建内核实例时显式注入工作空间、数据目录、凭据端口、系统能力和日志，不在模块导入时启动飞书或读取开发目录配置。

保留两种组装入口，共用同一份内核：

1. 独立飞书服务入口：保留既有部署方式，配置需要的飞书渠道。
2. 嵌入式入口：由纬舟启动，可先不配置飞书；配置后仍通过同一内核处理飞书消息。

嵌入式入口通过薄传输适配接入 Electron 工具进程的私有消息通道。Electron 特定 API 只存在于宿主/传输层，领域和用例不得引用 Electron。不能让 headless 模式被迫创建窗口。

正常使用打包后的应用不要求另装 Node.js、pnpm、构建工具或手动克隆 Agent-Team；真实 Claude/Codex CLI、Git 及其认证仍需环境检查，不承诺随应用捆绑第三方 CLI 或账户登录状态。

## 3. 产物与锁定

内核发布物包含：ESM 入口、生产依赖、协议 schema/类型、资源模板、迁移文件、许可清单和 manifest。原生模块按 macOS/Windows 与具体 CPU/Electron ABI 目标构建，不能将一个平台的 node_modules 复制到另一个平台。

纬舟发行包内装配匹配的内核产物。构建输出、解压缓存和 node_modules 不提交到桌面源码；构建脚本根据锁定信息取得产物并校验摘要。

工程阶段建立内核锁文件，至少记录：

| 字段                          | 用途                               |
| ----------------------------- | ---------------------------------- |
| kernelVersion、sourceCommit   | 可追踪的内核版本和 Agent-Team 提交 |
| artifact、sha256              | 明确来源与内容摘要，防止浮动依赖   |
| protocolVersion、capabilities | 客户端协议和能力兼容               |
| dataSchemaVersion、兼容范围   | 升级与旧数据读取约束               |
| platform、arch、runtimeAbi    | 目标系统、CPU 与原生模块兼容       |

锁文件字段是设计约定，当前没有真实内核包、版本号、摘要或发布地址，不创建伪造的可下载产物。

首版桌面与内核一起发行并锁定版本，不做用户无感的独立内核热升级。启动握手发现协议不兼容时显示明确错误，不能继续假定命令可用。

## 4. 数据与生命周期

数据库、工作区锁、任务和事件由内核独占业务写入权。纬舟不直连其数据库；非敏感界面偏好可由桌面单独保存。

每个数据目录需要内核实例锁。禁止独立服务与嵌入式内核同时打开同一数据目录执行任务；禁止两个消费者同时接收同一飞书应用事件并双重派发。首版不默认附着到未知的外部 Agent-Team 服务。

关闭窗口保留主进程/托盘与内核；完全退出先停止受理新任务、持久化停止意图、处理在途 CLI、确认退出并释放资源。无法确认子进程结束时显示失败与恢复要求，不能声称已安全停止。

升级前使用一致性备份；应用回退不自动降级已迁移的数据库。数据 schema 不兼容时选择匹配的备份恢复或前向修复，不能仅替换旧内核文件后启动。

## 5. 两仓联调与提交顺序

用户已授权为纬舟开发所需同步修改 Agent-Team。正常的内核解耦、接口/事件扩展、持久化、兼容性、测试和打包无需逐项重新请示。

1. 两仓分别检查 Git 状态和本仓规范；Agent-Team 从 OpenWiki 入口了解现有行为，生成页面不手动编辑。
2. 在 Agent-Team 编写最小共享改动，保留原飞书入口兼容并补相关回归测试。
3. 本地可以引用指定工作目录或明确提交构建的测试内核，设置显式开发模式；发行与 CI 禁止隐式读取相邻未提交源码。
4. 先提交/形成可追踪内核产物，再更新纬舟协议客户端、锁文件和装配；记录关联提交、兼容范围和验证证据。
5. 分别跑 Agent-Team 原有检查和纬舟检查，再验证打包后真实闭环与旧入口回归。
6. 两仓提交无法天然原子合并；通过兼容协议、先内核后客户端、锁定产物和关联记录保持可恢复，不依赖两个 main 同时更新。

允许同步改源码不表示可以自行切换生产服务、修改真实配置、移动业务数据或重新授权飞书应用。本轮不实施这些操作。

## 6. 完成验收

- 从干净检出和锁定配置可构建桌面包，不依赖开发者相邻目录。
- 打包后启动的确是锁定 Agent-Team 内核，版本和源提交可在诊断页核验。
- 没有飞书配置也能启动本机任务；配置后桌面与飞书共享同一业务状态。
- 原独立飞书入口仍能按原方式使用同一内核能力，不额外引入桌面运行依赖。
- macOS 与 Windows 分别验证原生依赖、凭据、中文/空格路径、进程终止和安装包启动。
- 未实现能力在握手能力清单中标明，客户端不能用模拟成功掩盖内核缺项。
