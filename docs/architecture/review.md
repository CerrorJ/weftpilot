# 架构与开发规范评审确认表

版本：v0.1。状态：**待用户确认**。本文件不代表已确认技术选型，也不授予正式开发、生产切换或发布权限。

## 已确认的需求与协作要求

- 产品名称：纬舟 / WeftPilot，公开独立仓库。
- 角色配置 Skill、CLI、模型；技能中心支持市场安装；角色创建衔接飞书控制台。
- 具有团队、项目、需求、任务、模型设置；任务绑定项目并清晰展示状态与进度。
- 项目展示 Git 地址和分支；桌面驱动现有能力并保留飞书渠道。
- `product-design` 放产品方案与原型；`main` 作为整个项目开发源码主线。
- 所有分支不加 `codex/` 前缀，`AGENTS.md` 使用中文。
- 正式开发将在另一台设备的 Codex 中进行；本轮先给架构设计与开发规范供确认。
- Superdesign 不使用付费生成功能，复用原创品牌素材。

## 建议决策（均待确认）

| 编号 | 建议 | 影响与替代方向 |
| --- | --- | --- |
| A1 | Electron + React + TypeScript；内核为模块化单体 | 优先复用 Node CLI 生态；若改 Tauri，需要另行评估 sidecar 和 Rust 集成成本 |
| A2 | 本机单设备、单所有者；AI 团队协作，暂不做多人账号/云同步 | 首版可闭环；多人和远程执行需要后续身份、隔离和同步设计 |
| A3 | 内核独立工具进程；关闭窗口继续，完全退出不承诺常驻 | 若要求退出后运行，需改为独立 daemon 并增加系统生命周期管理 |
| A4 | SQLite 业务表 + 持久事件，内核唯一写入；桌面/飞书调用同一套用例 | 避免渠道状态分叉；数据库驱动与打包需 M0 验证 |
| A5 | 首版一个项目一个主 Git 仓库，默认每 Run 一个 worktree | 便于隔离并发写入；非 Git 任务和多仓库需扩展模型 |
| A6 | 每次重试新 Run；审批续接同一 Run 的新片段；执行与验收分开 | 历史可解释，不能简单复用旧服务的会话状态 |
| A7 | 飞书先保证已有应用绑定/控制台辅助创建；自动创建以技术验证为准 | 无接口验证时不承诺全自动创建、授权或发布 |
| A8 | macOS 与 Windows 为首版发行候选，Linux 后续 | 需确认实际开发设备与首发系统，安排原生验证 |
| A9 | M0→M1 最小真实闭环→M2 对象/团队→M3 飞书/人工处理→M4 市场/发行 | 优先验证执行内核，再扩展完整页面与渠道 |

其中 A1、A2、A3、A8 最影响成本和产品范围，建议优先确认；其他项可一并确认或逐项调整。

## 进入开发前需技术验证的事项

- 实际开发设备的系统、CPU、CLI 版本与认证方式；Electron 打包后的 Node/SQLite/凭据兼容。
- 两种 CLI 可落实的工具/文件/网络限制、停止与续接语义，不能仅凭角色设置宣称已限制。
- 飞书列举/创建/配置应用的官方能力、所需身份和租户权限，避免把访问令牌误当管理权限。
- Skill 市场首个来源、元数据与许可，CLI 加载技能的位置与版本隔离方式。
- 旧服务迁移源提交、可复用代码的许可与历史数据是否需要迁移。
- 仓库开源许可证、品牌商标可用性、安装包签名与后续发行渠道。

“待验证”不要求此刻全部由用户解答：架构确认后由 M0 在开发设备验证；影响已确认范围时再报告具体差异。
