# 迁移、交付阶段与跨设备开发

状态：待确认。工程初始化及业务开发均未开始。

## 1. 现有能力如何复用

原服务：[CerrorJ/Agent-Team](https://github.com/CerrorJ/Agent-Team)。本轮根据现有源码与 OpenWiki 梳理边界；开发设备必须重新取得源码并记录当时提交，不假定文档与最新代码始终一致。

| 现有位置 | 建议迁移到 | 迁移注意 |
| --- | --- | --- |
| `src/cli/types.ts`、Claude/Codex adapter | `packages/adapters/cli` | 保留事件解析能力，补充能力矩阵与归一化版本；不固化模型枚举 |
| `src/cli/runner.ts`、`spawn-cli.ts`、`timeout.ts` | CLI 执行适配器 | 参数、超时、进程树终止、会话续接做平台验证 |
| `src/core/provider-error.ts` 及恢复逻辑 | CLI/provider 错误适配 | 区分认证、限流、网络、内容与执行故障，不盲目重试已发生的动作 |
| `src/core/workspace.ts` | Git/工作目录适配器 | 从单目录约定升级为显式 Project、Run、worktree 和目录锁 |
| `src/core/approval.ts`、澄清和方案流程 | application 人工处理用例 | 解耦飞书 ID，保留业务校验，改为持久状态与版本裁决 |
| `src/core/session-store.ts` 等 JSON store | SQLite 仓储 | 不复制生产数据；设计显式导入与版本映射后再迁移 |
| `src/im/lark.ts` 和卡片处理 | 飞书渠道适配器 | 保留消息/事件接入，但调用统一应用用例 |
| `src/mcp/app-tools-server.ts` | 内核工具入口适配器 | 工具调用绑定 Run 和权限，不直接绕过应用用例修改状态 |
| `src/app/runtime.ts`、`src/index.ts` | 按职责拆到内核组装与用例 | 不整份复制入口；现有共享状态包含飞书对象，需逐项解耦 |

优先迁移可独立测试的 CLI 解析、错误归一化和进程管理，再接状态与飞书。原服务可继续运行；不得让新旧服务同时消费同一批飞书事件并双重执行。联调先用专用测试应用和测试仓库，切换时明确停止旧消费者、完成在途任务对账后再启动新消费者。

不直接导入旧服务的 `.env`、CLI 登录文件、会话、聊天记录和运行目录。若以后需要导入历史数据，单独实现可预览、可回滚、保留外部 ID 映射的迁移工具。

旧代码迁移前核验许可和来源，记录路径、原提交、修改原因与保留测试；不因同属一个 GitHub 账号就省略来源说明。

## 2. 分阶段交付

不按时间承诺交付，按可验证闭环推进。每阶段交付代码、测试、演示步骤、实际完成项和剩余问题。

| 阶段 | 内容 | 退出条件 |
| --- | --- | --- |
| M0 技术验证与工程基线 | 锁定工具链；Electron main/preload/utility process 最小往返；SQLite 事务/备份/打包；系统凭据；CLI 环境与停止能力；飞书控制台能力验证；建立 CI | 实际开发设备可复现验证，候选平台问题有结论，不能用模拟数据声称集成成功 |
| M1 本机最小执行闭环 | Project、角色版本、一个 CLI、Task、Run、worktree、持久事件、停止、交付和人工验收；使用本地 Skill 固定版本 | 在测试 Git 仓库完成真实任务；重启状态可恢复；用户改动未受损；执行/验收可区分 |
| M2 产品对象与协作 | 需求版本、模型配置、第二个 CLI、团队/子任务、依赖、调度、角色试运行、草稿与变更版本 | 并发与依赖正确，配置变更不影响运行中快照，团队进度可解释 |
| M3 人工处理与飞书 | 澄清、方案/操作审批、飞书绑定和状态卡片、控制台辅助向导、跨渠道幂等 | 桌面/飞书操作同一对象；重复与过期卡片无效；审批续接与新 Run 重试可区分 |
| M4 技能市场与发行 | 市场来源适配、版本安装/升级/卸载、诊断包、备份恢复、签名/安装包、更新策略 | 可验证来源与版本；异常安装可恢复；候选系统安装/升级可复现；发布前核验许可证 |

M1 的最小角色编辑、项目页和任务页先打通真实能力，再按产品原型扩展；不先铺满八个页面而内核全部模拟。

建议首版发行目标为 macOS 和 Windows，Linux 后续；这是待确认建议。优先在实际开发设备验证，第二平台必须有原生验证，不能用跨平台编译成功替代运行验收。

## 3. 关键验证场景

- 正常任务：从项目仓库到真实 CLI 结果、交付证据和人工验收。
- 用户关闭窗口：任务持续执行；完全退出时行为明确且停止状态可信。
- 内核在启动 CLI 前后崩溃：不重复执行未知动作，不错误清理仍被使用的目录。
- 工作区脏文件、分支冲突、路径含空格/中文：阻塞原因明确，不覆盖原文件。
- CLI 启动失败、认证过期、限流、进程无响应和停止超时：稳定错误码与可理解的处理动作。
- 断线和重连：从游标补齐，重复事件不重复推进；日志洪水不阻塞控制事件。
- 飞书/桌面同时审批、重复点击、旧版本和过期决定：只裁决一次。
- 角色配置/Skill 升级后旧 Run 仍能解释；验收退回保留交付且修改创建新 Run。
- SQLite 升级失败、磁盘不足、凭据系统不可用：明确失败，可恢复，不降级为明文。

## 4. 另一台设备的 Codex 交接

1. 克隆 `main`，先读中文 `AGENTS.md` 和评审确认表；未收到架构确认时仅讨论和修改文档。
2. 根据用户确认更新决策状态；确认只适用于被确认范围，不扩展成可发布/可修改生产服务的授权。
3. 另行取得 Agent-Team 源码，记录迁移提交；若仓库不可访问，说明缺少的具体能力，不凭文件名重写假实现。
4. 可另克隆 `product-design` 参考交互，禁止把演示运行逻辑当生产能力；素材使用主分支中的 SVG。
5. 检测开发设备系统、CPU、Node/pnpm、Git、CLI、系统凭据和网络能力；再固定兼容版本。不要复制设计设备的依赖目录。
6. 使用不带 `codex/` 的功能分支开展 M0；按实际授权范围推进，不反复请求已经给出的许可。
7. 本机授权 CLI、飞书与模型凭据。只提交非敏感示例配置，不把授权状态传入仓库。
8. 每次交接记录当前分支/提交、实际实现、检查结果和剩余事项，不依赖会话记忆。

可直接交给新设备 Codex 的启动说明：

> 请先读取本仓库 AGENTS.md、README.md、docs/architecture/review.md 和开发规范，汇报当前评审状态。若用户已确认架构，先把确认记录落到文档，再按 M0 做最小技术验证和工程初始化；当前没有正式应用源码，不要宣称已有业务功能。以 Agent-Team 既有能力为迁移参考，产品交互参考 product-design 分支。分支不加 codex/，不改动旧服务的在线配置，不复制凭据与运行数据。每阶段提供可复现验证和剩余问题。
